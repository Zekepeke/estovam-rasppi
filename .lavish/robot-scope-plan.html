04 · Decisions needed now

Three small calls, each cheap to make, each blocking Phase 1

None of these need Tommy. They need you to pick, once, and let the code catch up to the choice.

Where does STT run?

✓ decided · move to Pi 5, in-process
Not chosen · stay on RUBIK

faster-whisper stays remote over HTTP on :8000. Zero code change, but costs a network hop and spends RUBIK compute that the LLM could use instead.

✓ Decided · Pi 5, in-process

Removes a server you have to keep alive on RUBIK and frees its NPU/GPU budget entirely for the LLM — the bigger latency win. Start with tiny.en; step up to base.en only if accuracy needs it.

Benchmark before you swap services/stt.py: write a small standalone script that runs the existing wake-word loop and a local faster-whisper instance in the same process, side by side — don't touch main.py yet. Say the wake word 10–15 times while it's transcribing a held buffer in the background, watching two things: the "Audio buffer overflow" warning already logged in hardware/audio.py, and whether any wake-word trigger gets missed or delayed. Clean run → swap services/stt.py's HTTP call for the local WhisperModel behind the same function signature, so main.py doesn't change. Contention → keep STT remote and revisit once Phase 2's latency instrumentation can show you where the time actually goes.

Which TTS provider?

✓ decided · keep ElevenLabs
✓ Decided · ElevenLabs

It works today, ~75ms first-audio with Flash/Turbo, and per-request voice_settings already gives you the emotion hook the chat designed for later. Zero engineering cost — no code change needed here.

Not now · Orpheus on RUBIK

Removes the cloud dependency and per-call cost, but RUBIK is already carrying the LLM, and it's still unbenchmarked ("🔵 Planned" in your own status notes). Revisit after the event bus exists, so a TTS swap doesn't land at the same time as an architecture change.

Confirmed: swapping TTS providers is exactly the kind of feature-shaped work you're deferring right now. ElevenLabs isn't a compromise — it's the right call while the priority is a working skeleton over a fully self-hosted stack.

What happens to the camera's JPEG?

✓ decided · route through Gemini
Not chosen · turn the camera off

Set CAMERA_ENABLED = False. Honest, but costs you the "sees" feature you explicitly want working, so this isn't the direction.

✓ Decided · Gemini as the AIEngine's second tier

Confirmed: no local vision model on RUBIK for now. services/llm.py today has no Gemini import at all — GEMINI_API_KEY and GEMINI_MODEL are leftover config constants nothing calls. The rule to add: if the turn includes an image, call Gemini multimodal (image + prompt in one request) instead of RUBIK's text-only llama-server. RUBIK stays the default for audio-only turns.

Cleanup that comes with this: LlamaLLM.stream_response() currently accepts an image_bytes argument it silently ignores. Once Gemini owns every turn that has an image, that parameter has no reason to exist on the RUBIK client — the branch belongs one level up, in whatever function decides which backend to call. Drop it from LlamaLLM rather than leaving a second dead parameter next to the one you just found.

On local vision (YOLO or similar) — not worth it right now: RUBIK is already carrying the LLM's RAM and GPU budget; a second model competes with it for the same resources. Gemini's multimodal API already answers "what am I looking at" for free-tier volumes, which is the feature you're after. Local detection earns its cost only for a different problem — continuous, low-latency tracking (say, keeping a face centered for head motion) rather than a per-query description — and that's a Phase 3+ conversation once there's a motor to point at what it finds.

# Desk Robot — agent conventions

## Architecture rules (locked)
- Pi 5 is the orchestrator. It speaks protocols to coprocessors
  (HTTP to RUBIK, serial to the motion board) — it never becomes one.
- Four seams only: AIEngine, CameraInterface, AudioSink, MotionInterface.
  New hardware gets a new implementation of an existing seam, not a new seam.
- Motion is event-driven. main.py emits state on EventBus; nothing
  downstream is ever imported by the core loop directly.
- No hardcoded hosts, ports, or model names outside config.py.

## Current topology (decided 2026-09-08 — update this block, not just config.py, when it changes)
- RUBIK Pi 3 is reached via its Tailscale address, set once in config.py.
  Never hardcode a LAN IP in README, .env.example, or code.
- STT runs locally on the Pi 5 (faster-whisper, in-process). RUBIK is
  reserved for the LLM.
- TTS is ElevenLabs. Not revisited until after the event bus ships.
- Vision: turns with an image go to Gemini multimodal (AIEngine's second
  tier); RUBIK's llama-server stays text-only and does not take images.

## Deferred until Tommy's motion platform lands
- SerialMotion, real pose ranges, baud/axis conventions.
- Emotion-tag parsing — there is no motion consumer for it yet.
Do not scaffold these speculatively; MockMotion is the seam contract.

## Running it
- `python main.py` is the only entry point. Files at repo root
  (parrot.py, test_wakeword.py) are throwaway hardware probes, not
  part of the app — do not import from them.

Moving STT to Pi 5 could contend with wake-word polling. Both need the mic stream; local Whisper inference on a Cortex-A76 while openwakeword is also listening hasn't been measured on this board. See the benchmark steps in §04 — run them before touching services/stt.py, not after.

OK

Accepted for MVP: Gemini as a vision tier reintroduces a cloud dependency the RUBIK path was partly meant to avoid.
